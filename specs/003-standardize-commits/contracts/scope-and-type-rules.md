# Scope, Type and Validation Rules

**Feature**: `003-standardize-commits` | Single source of truth for `commit-classify.sh` and `commit-validate.sh`.

## 1. Path to scope (first match wins)

| Order | Path pattern | Scope |
| :--- | :--- | :--- |
| 1 | `apps/<name>/**` | `<name>` (for example `idea-collector`, `commifra`) |
| 2 | `.github/**` | `ci` |
| 3 | `infra/**` (top level) | `infra` |
| 4 | `packages/**`, `shared/**` | `shared` |
| 5 | `scripts/**` | `scripts` |
| 6 | anything else | `repo` |

**Companion files** do not count toward the multi-scope warning: lockfiles (`pnpm-lock.yaml`, `go.sum`, `package-lock.json`), anything under `specs/` or `docs/`, and test files whose sibling source file is in the same scope. They take the scope of the main change.

**The `deps` scope**: `deps` is a commit-only scope used when the staged set is lockfiles and dependency manifests only. It is not derived from a path, and it replaces the path-derived scope for that case.

**Redundant scope**: when the scope equals the type (`ci` with type `ci`, `infra` with type `infra`), the scope is omitted and the JSON `scope` is `null`, giving `ci: …` and not `ci(ci): …`. A different type keeps the scope, for example `fix(ci): …` or `infra(idea-collector): …`.

**Single scope rule**: if exactly one non-companion scope remains, use it. If several remain, set `warnings: [multi-scope]`, leave `scope` null, and fill `split_suggestion`. If everything is `repo`, omit the scope for pure chores and docs.

## 2. Type heuristics (evidence only; a person confirms)

| Evidence in the staged set | Proposed type |
| :--- | :--- |
| Only `specs/*/spec.md` and `specs/*/checklists/requirements.md` | `req` |
| Only infrastructure definitions (`infra/**`, `apps/*/infra/**`) | `infra` (scope still from the path map, for example `infra(idea-collector)`) |
| Only `*.md`, `docs/`, `specs/`, `README*` (anything not matched by the `req` row) | `docs` |
| Only test files (`*_test.go`, `*.test.*`, `*.spec.*`, `tests/`) | `test` |
| Only `.github/**` | `ci` |
| Only lockfiles and dependency manifests | `build`, with scope `deps` (`build(deps)`) |
| Only whitespace/format changes (`git diff --ignore-all-space` is empty) | `style` |
| Only files under `.claude/`, `.agents/`, `.specify/`, config, scripts without behaviour change | candidates `chore`, `build` |
| New source files | candidates `feat`, `refactor` |
| Modified source files | candidates `fix`, `feat`, `refactor`, `perf` |

When the evidence does not give exactly one answer, `type` is `null` and `type_candidates` is ranked as above.

## 3. Breaking-change hints

A hint is raised (and the commit then requires `--breaking` or `--no-breaking`) when the staged set contains:

- a deleted or renamed file under `apps/*/backend/`, `packages/`, `shared/`, or `contracts/`
- a changed `variable` or `output` block in `*.tf` that removes or renames a name
- a changed API route registration or a removed exported symbol in a staged hunk
- a deleted migration, schema or table definition

Hints are advisory; only the contributor decides.

## 4. Message validation

| Rule id | Severity | Check |
| :--- | :--- | :--- |
| `empty-message` | error | Not empty or whitespace-only |
| `type-invalid` | error | `type` is one of `feat fix chore docs style refactor perf test build ci req infra` |
| `scope-invalid` | error | When present, matches `[a-z0-9][a-z0-9-]*` |
| `header-format` | error | Header matches `^type(scope)?!?: summary$` with exactly one `: ` |
| `header-too-long` | error | Header length is strictly less than 100 characters |
| `uppercase-summary` | error | First character of the summary is not an uppercase letter |
| `trailing-period` | error | Header does not end with `.` |
| `not-imperative` | warning | First word does not end in `ed` or `ing` and is not a third-person `-s` verb (small allowlist of exceptions) |
| `missing-blank-line` | error | Line 2 is blank when a body or footer follows |
| `breaking-footer-missing` | error | `!` in the header requires a `BREAKING CHANGE:` footer, and the reverse |
| `footer-format` | error | Footer lines match `Token: value` |

Merge and rebase messages generated by git (`Merge ...`, `Revert ...`, `fixup!`, `squash!`) are accepted when `git_state` is `merge` or `rebase`.

Every failed rule is reported (not just the first) with its `severity` and a `suggestion` where it can be computed. `validate` exits `1` and `commit` refuses the message only when at least one **error** is present; warnings are shown and never block, because the imperative-mood check is a heuristic (see research D6).
